# Celestial context — Infinite 0.11

The empty cockpit view had several concrete causes. A system's child catalogue was culled when its reference radius exceeded forty render units, hiding other planets during ordinary planetary flight. The local depth range also clipped distant light proxies. The cockpit scope displayed only one target. Background stellar sprites could shrink below one pixel, and the sky omitted the addressed galaxies in neighbouring root cells.

## Existing objects, visible from the ship

`extractCelestialContacts` is a read-only scene adapter. It consumes the current system and its asynchronously cached planet catalogue, deriving each body's true ship-relative bearing, distance, angular radius, identity and occultation. It never moves a body or changes a descriptor. All existing planets and the sun now appear on the scope and in a compact cockpit contact list, with ranges and ahead/aft/occulted status.

Unresolved planets and the sun have angular light proxies that remain inside the local projection range. Their physical positions and travel distances remain authoritative. Forward labels identify small planets; clicking a light or contact-list row selects the same address used by Y/J navigation. Large planetary geometry remains generated by the existing mesh and terrain systems. Spherical occultation prevents lights and pick targets appearing through nearer planets. Known occulted destinations remain selectable through the instrument list.

The galactic sky requests the existing second-level stellar population asynchronously: up to 19,000 addressed stars, retaining the same IDs and samples as lower detail levels. Its unresolved points have a resolution-dependent minimum footprint. This applies the antialiasing intent of Hyperion's `flight/shaders.hpp::stars` to Infinite's actual stellar records. It uses the already ported radial glow and HDR composition. The existing gas samples contribute quiet extended emission. Visible stars can now be clicked and entered as the corresponding systems.

Existing galaxies from neighbouring root catalogues supply light in the outward-facing hemisphere. A separable smooth spatial weight gives at most eight active catalogues, with weights that sum to one and remain identical for the same galaxy when the root coordinate frame changes. These are actual Galaxy addresses, so a selected light is also a valid long-voyage destination. The additional catalogue demand uses the existing worker limit, LRU cache and 32 MiB CPU cache budget. It does not generate world geometry on the rendering thread.

The flight sky is composed before terrain and local geometry. Local opaque depth always wins, including when a terrain tile's physical distance exceeds the sky's projection shell. The Original inspector path retains its prior pass order. All flight modes see the same contacts and structures; Hyperion and Hybrid use the existing ported glow and tonal presentation.

## Preservation and validation

Checkpoint `6232423` preserves Infinite 0.10 before these changes. No generator, seed, spatial-coordinate implementation, ship dynamics or persistent ship schema was changed. The galaxy records, system catalogues, orbital positions, terrain, rocks, minerals and atoms remain authoritative.

Presentation tests cover real celestial addresses and distances, bodies beyond the far plane, foreground/background occultation, selection identity, bounded sky catalogues and continuous root exposure. The native cockpit fixture checks a distant planet can be picked at its true bearing, a rendered star selects the corresponding System address, identical camera/geometry across three rendering modes, landing/launch and nano flight. Captures include the system contact view and both outward and galaxy-facing skies.

All 23 release tests passed in 164.89 seconds. The signed macOS 0.11 package also passed fresh-start and saved-flight restart checks. Eighteen generator, coordinate, simulation, ship-dynamics and main-loop source files were verified byte-for-byte against the checkpoint; hashes are included with the evidence.

Release logs, before/after captures, measurements and preservation hashes are stored in [celestial-context](celestial-context/).

## Measured comparison

Metal, 1440 × 900, the same seed, physical orbital viewpoint and fixed visual time. Both builds ran the landing/launch/shrinking fixture. The after run adds forty frames to verify the distant-planet view. Frame timing is VSync limited; the CPU/GPU samples below use the same stationary orbital phase, dropping five transition frames at each end.

| Measurement | 0.10 before | 0.11 after |
|---|---:|---:|
| Galaxy-facing addressed stars | 4,448 | 16,889 |
| Addressed galaxies in the outward view | 0 | 63 |
| Complete-flight median frame time | 16.66 ms | 16.66 ms |
| Complete-flight p95 frame time | 16.98 ms | 17.33 ms |
| Stationary-orbit median rendering CPU time | 2.38 ms | 3.26 ms |
| Stationary-orbit median GPU time | 3.76 ms | 3.48 ms |
| Peak process RSS | 131.31 MiB | 141.73 MiB |
| Final CPU geometry cache | 11.61 MiB | 12.67 MiB |

The extra scene extraction costs about 0.88 ms of rendering CPU time in that phase. Peak RSS grows by 10.42 MiB (7.9%); the worker limit, geometry cache budget and HDR target allocation stay unchanged. The small GPU-time difference is within run-to-run variation, not evidence of an optimisation.
